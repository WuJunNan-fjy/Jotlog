## 一、问题是什么

用户反馈"飞书发过来的附件不能下载，OSS 里没有附件"。

排查后确认（有截图证据，条目 #67/#69）：

| 条目 | 来源 | 现象 | 结论 |
|---|---|---|---|
| #69 | 网页上传 docx（21KB） | 详情有"附件 · 1"，下载正常 | OSS、下载接口、前端、部署版本**整条链路都是好的** |
| #67 | 飞书 `视频制作教程.zip`（约 500MB） | 详情里**连附件区块都没有**，只有正文 `[文件] 视频制作教程.zip` | 异步补挂在"从飞书下载"这一步失败，`attachments` 表没写入 |

用户实测对照：**小文件能成功，500MB 文件必失败**。

### 根因（官方文档实锤）

飞书「获取消息中的资源文件」接口（`GET /open-apis/im/v1/messages/:message_id/resources/:file_key`）有硬限制：

- **不加分片：只能下载 < 100MB**；≥100MB 直接返回错误码 **234037**（`Downloaded file size exceeds limit`）；
- `type=file`：支持 `Range` 请求头分片下载，**单片不得超过 32MB**；
- `type=image`：**不支持 Range**，≥100MB 图片无法下载（飞书产品限制，无解，只能告警）。

原代码（[FeishuChannel.java](file:///f:/ideaCode/personal/Jotlog/src/main/java/com/jotlog/channel/feishu/FeishuChannel.java) 的 `download()`）只走整包下载，234037 时记一条 error 日志就返回 null，Pipeline 静默跳过 —— 所以界面上毫无感知。

### 排除过的其他嫌疑（都不是根因，别再查）

1. ~~服务器 jar 是旧版~~：#69 能上传 OSS 证明新版（10-11 的 `acbfbaf`）已部署；本地 `target/jotlog.jar` 构建于今天 16:21。
2. ~~飞书权限不足~~：官方文档明确该接口用 `im:message` 即可（已配置），且小文件成功。
3. ~~SDK `success()` 误判~~：核对了 SDK 2.8.5 源码，HTTP 200 时 code 保持默认 0，`success()` 返回 true，判定正确。
4. ~~OSS 配置/GC 误删~~：#69 正常；GC 的 key 形状校验也不可能删掉未上传过的对象。

## 二、这次改了什么（5 个文件，已 `mvn compile` 通过）

数据流新链路（仅 ≥100MB 的 file 类型走新分支，<100MB 一切照旧）：

```
飞书 234037
  → ResourceTooLargeException（信号，不再静默 null）
  → Pipeline.saveLargeFile()
      ├─ 临时文件 + DigestOutputStream（边下边算 sha，不用回读 500MB）
      ├─ FeishuChannel.downloadRange()  16MB/片，HTTP 206 循环拼接
      └─ IngestService.saveAttachmentFile()
           ├─ OSS：uploadFile 分片上传（5MB/片，taskNum=1，无 checkpoint）
           ├─ local：Files.move（跨设备退化为 copy）
           └─ attachments 落库 → finally 删临时文件
```

| 文件 | 改动 |
|---|---|
| [FeishuChannel.java](file:///f:/ideaCode/personal/Jotlog/src/main/java/com/jotlog/channel/feishu/FeishuChannel.java) | ① 常量 `CODE_RESOURCE_TOO_LARGE=234037`；② `download()` 撞 234037 抛 `ResourceTooLargeException`（unchecked，其他失败仍返回 null）；③ 新增 `downloadRange(messageId, fileKey, type, OutputStream)`：绕开 SDK 的 `messageResource().get()`（它只认 HTTP 200，206 会被当 JSON 错误体），直接调底层 `Transport.send` 复用 token 注入，自己发 `Range` 头、收 206、解析 `Content-Range` 取总长、解析 JSON 错误码；④ `fetchRangeWithRetry()`：**单片 3 次尝试**，4xx 业务错误立即终止（`NonRetryableRangeException`），网络异常/429/5xx/空片退避 0.5s、1s 重试——失败片未写盘，重试不会污染已下载内容；⑤ 内部类 `ResourceTooLargeException`、`NonRetryableRangeException`、record `RangePart` |
| [StorageService.java](file:///f:/ideaCode/personal/Jotlog/src/main/java/com/jotlog/storage/StorageService.java) | 门面新增 `storeFile(Path source, long size, filename, mime, sha256)`：流式落存储，不读进堆 |
| [LocalStorageService.java](file:///f:/ideaCode/personal/Jotlog/src/main/java/com/jotlog/storage/LocalStorageService.java) | `storeFile`：同 sha 跳过；先 `Files.move`（同盘零拷贝），失败且 target 不存在时退化为 `Files.copy`（兼容 systemd `PrivateTmp` 跨设备） |
| [OssStorageService.java](file:///f:/ideaCode/personal/Jotlog/src/main/java/com/jotlog/storage/OssStorageService.java) | `storeFile`：`doesObjectExist` 去重后走 `OSSClient.uploadFile(UploadFileRequest)`（multipart，5MB/片、顺序上传）。⚠️ 该方法签名是 `throws Throwable`，已 catch Throwable 包成 StorageException |
| [IngestService.java](file:///f:/ideaCode/personal/Jotlog/src/main/java/com/jotlog/core/IngestService.java) | 新增 `saveAttachmentFile(...)`（`@Transactional`）：流式存储→元数据落库→finally 删临时文件，失败只 warn 返回 0 |
| [Pipeline.java](file:///f:/ideaCode/personal/Jotlog/src/main/java/com/jotlog/core/Pipeline.java) | `backfillAttachments` 捕获 `ResourceTooLargeException`：image 打 warn（飞书不支持图片分片），file 调新方法 `saveLargeFile()`：临时文件 + `DigestOutputStream` + `downloadRange` + `saveAttachmentFile`，双层 finally 兜底清理 |

### 关键技术决定（当时为什么这么写）

1. **堆内存安全**：500MB 不能进 byte[]（服务器 `-Xmx512m` 必 OOM）。下载侧堆内峰值 = 16MB 一个 Range 片；上传侧 OSS SDK 自己切片读磁盘。
2. **sha 边下边算**：`DigestOutputStream` 包在文件流外，下载完直接拿摘要，省一次 500MB 回读。
3. **为什么绕开 SDK 高层封装**：SDK 的 `MessageResource.get()` 对非 200 一律 `UnmarshalRespUtil` 反序列化，分片成功的 206 会被误判抛异常。底层 `Transport.send` 已核对源码：除 504 重试/抛异常外，**其他状态码（含 206、4xx）原样返回 RawResponse**，token 注入仍由 SDK 完成。
4. **去重口径不变**：存储侧 `doesObjectExist`/`Files.exists`，DB 侧 `ON DUPLICATE KEY UPDATE id=id`，与小文件路径完全一致。
5. **单片 16MB**：飞书上限 32MB，取一半留余量；OSS 侧 5MB/片是其官方推荐区间。

## 五、排查过程中沉淀的事实（下次直接用）

- 飞书资源接口：路径 `/open-apis/im/v1/messages/:message_id/resources/:file_key?type=image|file`；权限 `im:message` 即可；限制 <100MB（file 可 Range 分片、单片 ≤32MB，image 不可分片）；错误码 234037=超限。
- lark oapi SDK 2.8.5（已核对本地 sources jar）：
  - **超时**：`Client.Builder` 不调 `requestTimeout()` 时，`initHttpTransport` 走 `OKHttps.defaultClient = create(0, MILLISECONDS)`，即 OkHttp `callTimeout(0)`（无总超时）；connect/read/write 用 OkHttp 默认 10s，但 readTimeout 是包间隔不是总时长；
  - `MessageResource.get()`：**HTTP 200 才算成功**，其他码走 JSON 错误反序列化 → 不能用于 206 分片；
  - 底层 `com.lark.oapi.core.Transport.send(Config, RequestOptions, method, path, Set<AccessTokenType>, req)` 是 public static，token 自动注入，非 504 响应原样返回 `RawResponse`（`getStatusCode()/getBody()/getHeaders()/getFileName()`）；
  - 自定义请求头：`RequestOptions.newBuilder().supportDownLoad().headers(Map<String,List<String>>).build()`，`Range` 头可透传（ReqTranslator 只补 UA/Authorization/RequestId，不覆盖业务头）；
  - `Client.accessToken().getConfig()` 可拿到内部 Config（public），是复用 Transport 的入口。
- OSS SDK 3.17.4：`UploadFileRequest` 没有无参/单 bucket 构造器（3.17.3 时期的写法不通用，本次编译踩过），用 5 参构造器 `(bucketName, key, uploadFilePath, partSize, taskNum)`；`OSS.uploadFile` 声明 `throws Throwable`。
- 附件 DB 判定技巧：详情页有没有"附件"区块 = `attachments` 表有没有该 entry_id 的行（前端 `v-if="attachments.length"`）；排查时不用查表，看界面即可定性。
