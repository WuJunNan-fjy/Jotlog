## 0. 先回答你的核心疑问

你问："飞书发一条消息就记录到我的网站上了？"

**准确的说法是**：不是"记录到网站"，而是**记录到你自己服务器上的一个 SQLite 文件里**。你打开的"网站"只是这个文件的一个查看界面。

这个区别很重要，我下面会讲透。

---

## 1. 数据到底在哪：完整心智模型

### 1.1 只有一个数据源

Jotlog 部署完之后，**你的所有记录只存在于一个地方**：

```
你的公网服务器
└── /var/lib/jotlog/
    ├── jotlog.db          ← ★ 所有数据在这里，一个 SQLite 文件
    ├── jotlog.db-wal      ← WAL 模式的技术副产物
    ├── jotlog.db-shm
    └── attachments/       ← 图片和文件，按年月分目录
        └── 2026/
            └── 10/
                └── a1b2c3.png
```

**就这些。** 没有云数据库，没有第三方存储，飞书不存你的任何东西。

### 1.2 飞书只是入口，不是存储

这是最容易误解的地方，我用一张表说清：

| 你以为 | 实际 |
|---|---|
| 记录存在飞书里 | ❌ 飞书只是**消息的过路管道** |
| 记录存在网站里 | ❌ 网站只是**读这个文件的界面** |
| 关掉网站就看不到了 | ❌ 关掉网站**数据还在**，换个浏览器打开照样看 |
| 飞书挂了数据就没了 | ❌ 飞书挂了**数据完全不受影响** |

**打个比方**：飞书是**投递员**，你的服务器是**收件箱**，那个 `.db` 文件是**里面的东西**。

投递员罢工（飞书宕了、政策变了、你把它删了），收件箱里的东西**一样都不会少**。这也是为什么 v0.3 强调"通道即配置"——通道可以换，数据不能动。

### 1.3 三个端看到的是同一份数据

```
手机飞书 ──┐
手机网页 ──┼──>  你的服务器 ──> /var/lib/jotlog/jotlog.db
电脑网页 ──┘                      （唯一数据源）
```

**"互通"就是这么实现的**——不是什么同步魔法，就是三个客户端连同一个数据库。你在手机上记的东西，电脑上刷新就能看到；反之亦然。

**延迟**：飞书消息到入库约 200ms，网页端刷新即时可见。不存在"等同步"。

## 2. 一次记录发生的完整过程

以"在飞书发一条 GitHub 链接"为例，逐步拆解：

```
T+0ms     你在飞书里把链接发给「随手记」机器人
          │
T+10ms    飞书服务器收到你的消息
          │
T+50ms    飞书通过 WebSocket 长连接把消息推给你的服务器
          │   （这个连接是你服务器主动建立的，一直在跑）
          │
T+60ms    jotlog 进程收到 aibot_msg_callback 回调
          │
          ├─→ ① 幂等检查：这个 message_id 见过吗？
          │      没见过 → 继续
          │
T+65ms    ② 立即入库（同步，<5ms）
          │      写入 jotlog.db，此时 raw_input = "https://github.com/libi/tfo"
          │
T+70ms    ③ 立刻回复回执 ★这一步必须在最前面
          │      飞书里你看到：✓ 已存 #a1b2
          │
          ├─→ ④ 丢进异步队列，立刻返回
          │
T+80ms    返回 HTTP 200，连接回到空闲
          │
          ╰─→ 后台 goroutine 开始跑（此时你已经看到回执了）
                │
T+200ms     链接抽取：识别出这是 GitHub URL
                │
T+500ms     调 GitHub API：拿到 star 数、语言、描述、topics
                │
T+600ms     类型判定：repo（开源项目）
                │
T+700ms     AI 打标签（如果开了）：#开源 #待读 #工具
                │
T+800ms     更新数据库，补全元数据
                │
T+900ms     （如果开了飞书卡片回执）给刚才那条消息补一张卡片
```

### 关键设计：为什么回执必须在最前面

**因为飞书有响应超时**。如果先抓元数据再回复，整个流程可能 3-5 秒，遇到目标站慢或者 API 限流就超时了，用户体验变成"发出去没反应"。

所以 Jotlog 的铁律是：

> **入库 → 回执 → 异步增强。永远不要让慢操作阻塞确认。**

元数据是"锦上添花"，回执是"职责所在"。你 200ms 内就知道存没存上，标题和 star 数 800ms 后自己补上。

## 3. 平时怎么用：三个场景

### 场景一：手机上看到好内容（最常用）

```
飞书 App → 搜索「随手记」→ 进入会话 → 粘贴链接 → 发送
```

**回执示例**：

```
✓ 已存 #a1b2
karakeep-app/karakeep
29.4k star · TypeScript · 自托管书签工具
```

不是干巴巴一句"已保存"，而是**直接把抓到的关键信息回给你**。这样你不用切回应用去确认。

**支持的输入**：

| 你发的 | Jotlog 做什么 |
|---|---|
| 一条链接 | 抓标题、描述、封面、站点名 |
| GitHub 链接 | 额外抓 star 数、语言、最后提交时间、topics |
| B站/YouTube 链接 | 抓视频标题、封面、时长 |
| 一段话 | 原样存为纯文本，AI 自动打标签 |
| 一张截图 | 存进 attachments/，本地不丢 |
| 一个文件 | 存进 attachments/，按 sha256 去重 |
| 多个链接混在一段话里 | 全部抽出来，主记录存整段 |

### 场景二：电脑上一键秒记

这是**我认为你日常用得最多、也最爽的场景**。

```
在 VS Code 里看到一段代码
→ 全选 Ctrl+C
→ 按 Alt+Shift+F
→ 屏幕中间弹一个小输入框（你的 IDE 焦点还在原处）
→ Ctrl+V
→ 回车
→ 小框消失
```

**整个过程手完全不用离开键盘。** 从"看到"到"存好"约 1.5 秒。

**为什么这个设计比飞书还重要**：电脑前的时间往往是最专注的，任何"切窗口"的成本都会打断你。这个交互是从 `libi/tfo` 抄的，它虽然是冷门项目，但这一点做得对。

**技术实现**：PWA 做不到真正的全局快捷键（浏览器权限限制）。所以需要配一个**桌面壳**：

```
轻量方案（推荐先用这个）：
  - 装个 AutoHotkey（Windows）/ Hammerspoon（macOS）
  - 写 5 行脚本：快捷键触发 → 打开 jotlog 网址 + 自动聚焦输入框
  - 或者直接用系统的快捷键功能绑定 URL

进阶方案（M4）：
  - Tauri 打一个 3MB 壳，Rust 侧监听全局快捷键
  - 首次呼出时显示一个原生浮窗，输入后调 jotlog 的 API
  - 这个壳只做输入，其余全走 API
```

**我建议先用 AutoHotkey 方案**——五分钟搞定，不引入打包复杂度。等你确认这个交互真的好用，再考虑做 Tauri 壳。

### 场景四：早上收到回顾（对抗"存了不看"）

每天早上 9 点，飞书里收到一条：

```
┌────────────────────────────────┐
│ 昨日回顾 · 10月6日              │
│                                 │
│ 昨天记了 5 条：                 │
│  · 2 个开源项目                 │
│  · 1 段视频                     │
│  · 2 条金句                     │
│                                 │
│ ── 三天前你存过 ──             │
│                                 │
│ 📌 那个用 SQLite 做全文检索的   │
│    项目后来自己实现了分词       │
│    [打开]                       │
│                                 │
└────────────────────────────────┘
```

**下半部分是核心**。不是给你看昨天的（昨天的你刚记完，没意义），而是**随机重现一条三个月前的旧记录**。

这个机制的作用是"复利"：你存的东西开始沉淀，偶尔重逢，某个时刻正好需要，就是它的价值兑现时刻。

**这一条决定 Jotlog 是"=web 收藏夹"还是"你的第二大脑"。** 但它是 M3 的功能，先不做。

## 4. 数据安全：三个层次

### 4.1 数据不会丢

| 风险 | 保护 |
|---|---|
| 飞书挂了 | 数据在你自己服务器，飞书只是入口 |
| 服务器磁盘坏 | **需要你自己配备份**（见 4.2） |
| 你把应用删了 | 数据还在，`jotlog.db` 照常能用 |
| 平台改政策 | 换通道即可，数据格式不变 |

### 4.2 备份（重要）

**SQLite 不能直接 `cp`**——WAL 模式下会拷到不一致状态。

```bash
# 方式一：在线备份（不需停机，推荐）
sqlite3 /var/lib/jotlog/jotlog.db ".backup '/backup/jotlog-$(date +%F).db'"

# 方式二：VACUUM INTO（也能拿到一致快照）
sqlite3 /var/lib/jotlog/jotlog.db "VACUUM INTO '/backup/jotlog-$(date +%F).db'"
```

**建议加个 cron**：

```cron
# 每天凌晨 4 点备份，保留 30 天
0 4 * * * sqlite3 /var/lib/jotlog/jotlog.db ".backup '/backup/jotlog-$(date +\%F).db'"
30 4 * * * find /backup -name 'jotlog-*.db' -mtime +30 -delete
```

> 你有 systemd 和 rsync 的部署经验，junan 项目应该也在做类似的事——**同一个套路直接复用**。

### 4.3 附件也要备份

`.db` 只是一半，另一半是 `attachments/` 目录（图片和文件）。两个一起备份才算完整。

## 5. 开源策略（v0.5 新增）

你选了开源，这改变几件事：

### 5.1 许可证：MIT

**选 MIT 的理由**：

| 许可证 | 意味着 |
|---|---|
| **MIT** | 别人可自由使用、修改、商用，只需保留版权声明。**门槛最低，利于传播** |
| AGPL-3.0 | 别人改了代码做成网络服务必须开源。**会劝退一部分人** |
| Apache-2.0 | 多了明确的专利授权。比 MIT 长，法律场景更严谨 |

参考对象：`libi/tfo` 是 MIT（你我都看了），`Memos` 是 MIT。如果我直接参考 tfo 的产品设计，MIT 已经覆盖了。

**但内核代码我要自己写**——因为 MIT 允许抄，AGPL 不允许。为了开源后法律关系清晰，我选择：

- ✅ 参考 `tfo` / `Memos`（都是 MIT）的**设计思路和交互模式**
- ❌ 不复制任何 AGPL 项目（Karakeep / Readeck / Linkwarden）的代码
- ✅ 内核 100% 自写

### 5.2 开源后必须补的工作

这是选开源的实际代价，我提前列出来：

| 工作项 | 耗时 | 为什么必须 |
|---|---|---|
| **README** | 2 小时 | 决定有没有人 star。必须包含：一句话价值主张 + 5 行快速开始 + 截图/GIF |
| **零配置可跑** | 1 小时 | 试用者最怕配环境。`git clone && make build && ./jotlog` 就能跑 |
| **健康检查端点** | 30 分钟 | 让用户能确认"装好了"，也是 CI 的基础 |
| **配置项文档化** | 1 小时 | config.example.toml 每个字段都要有中文说明 |
| **CI（构建 + 测试）** | 1 小时 | 多平台构建验证，至少保证 Linux/macOS/Windows 能编过 |
| **贡献指南** | 30 分钟 | CODE_OF_CONDUCT.md，GitHub 开源惯例 |
| **Issue/PR 模板** | 20 分钟 | 降低维护成本 |
| 合计 | **约 1 天** | |

**这些不是负担，是开源的必要成本。** 而且它们对自用也有价值——比如"零配置可跑"会让你自己未来重装时省事。

### 5.3 依赖收敛（开源的硬约束）

这是选开源后**必须提前做的取舍**：

| 依赖 | 自用时的选择 | 开源时的问题 | 方案 |
|---|---|---|---|
| 分词 | `gojieba`（cgo） | 破坏 `CGO_ENABLED=0` 交叉编译 | **改用纯 Go 分词库，或把分词做成可选插件** |
| 数据库驱动 | `modernc`（纯 Go） | ✅ 无问题 | 保持 |
| Web 框架 | Gin | ✅ 无问题 | 保持 |
| 前端 | Preact | ✅ 无问题 | 保持 |

**分词是唯一需要做取舍的依赖。** 三个方案：

1. **内置一个简单的分词器**（按标点+停用词切，不追求准确）—— 最省事，搜索质量一般
2. **内置 Go 实现的 jieba**（`github.com/yanyiwu/gojieba`，纯 Go + embed 词典）—— 体积会大几 MB，但能用
3. **分词做成可选编译标签**（默认不带，`-tags jieba` 才启用）—— 最灵活但复杂度高

**我倾向方案 2**。理由：中文搜索是 Jotlog 的核心竞争力，开源用户第一件事就是试搜索，如果默认搜不了中文，项目就废了。多几 MB 二进制体积是可以接受的交换。

```markdown
