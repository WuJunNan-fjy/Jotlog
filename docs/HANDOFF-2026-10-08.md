## 三、今天踩的五个坑（都记在文档里了，别再踩）

### 坑 1：`1191 Can't find FULLTEXT index`

**现象**：`MATCH(raw_input) AGAINST(...)` 报错。
**根因**：MySQL 要求 `MATCH()` 的列与索引定义**完全一致且顺序相同**，
不是"能用索引前缀"。三列联合索引下即使只搜一列也要写全。
**修法**：索引定为 `(raw_input, title, ai_summary)`，查询一律写全三列。

### 坑 2：`NATURAL LANGUAGE MODE` 会静默失效

**实测**：3 条数据搜「沿途」score=0；22 条时 score=1.80。
**根因**：该模式把「出现在 >50% 行里」的 token 当停用词丢掉。
配 ngram 分词器后中文极易触发，**且不报任何错**。
这不是"数据量少的正常现象"，而是**随数据分布随机失效的设计缺陷**。
**修法**：应用层改用 `IN BOOLEAN MODE`（无阈值，行为确定）。

### 坑 3：ngram 会丢掉含 `a`/`i` 的英文词

**这个最要命**：`Java` 被切成 `Ja`/`av`/`va`，三个 bigram **全含 a 全被丢** → 永远搜不到。
而 `Boot`→`Bo`/`oo`/`ot` 不含停用词 → 正常。

**受控实验**（只差一个字母）：

| 词 | 含字符 | 命中 |
|---|---|---|
| `Zaza` | 含 **a** | ❌ 0 |
| `Zeze` | 含 e | ✅ 1 |
| `Zizi` | 含 **i** | ❌ 0 |
| `Zozo` | 无停用字符 | ✅ 1 |

**修法**（已在服务器上执行）：
```sql
SET GLOBAL innodb_ft_enable_stopword = 0;
ALTER TABLE entries DROP INDEX ft_search;
ALTER TABLE entries ADD FULLTEXT INDEX ft_search (raw_input, title, ai_summary) WITH PARSER ngram;
```

⚠️ **`SET GLOBAL` 重启失效，必须写进 `my.cnf`**：
```ini
[mysqld]
innodb_ft_enable_stopword = 0
```

**应用层已加兜底**：全文返回空时降级 `LIKE`，配置丢了只是变慢，不会搜不到。

### 坑 4：`Unsupported character encoding 'utf8mb4'`

**根因**：JDBC URL 里 `characterEncoding=utf8mb4` 无效。
`utf8mb4` 是 MySQL 字符集名，但这个参数走 Java 的 `String.getBytes(charset)`，
Java 里没这个字符集。
**修法**：写 `characterEncoding=UTF-8`。

### 坑 5：飞书 `Client.im()` 返回 null（NPE）

**现象**：编译过、启动正常、能收消息，**但回执时炸**。
**根因**：`new Client()` + `setConfig()` 只塞了配置，
`im`/`contact`/`bot` 等几十个 service 字段全靠 `Client$Builder.build()` 注入。
**修法**：
```java
Client.newBuilder(appId, appSecret)
      .appType(AppType.SELF_BUILT)
      .openBaseUrl(BaseUrlEnum.FeiShu)
      .build();
```
已加启动自检：`im()` 为 null 直接 log.error。

## 七、铁律（改代码前先看）

1. **`raw_input` 永不被 UPDATE 触碰**——那是用户原话。
   `JdbcEntryRepository.applyAiResult()` 的 SQL 里刻意不出现 `raw_input`。
2. **AI 是"补充"不是"润色"**——`note`（金句）类型完全跳过 AI，不改用户一个字。
3. **入库 → 回执 → 异步增强**，顺序不可调换。
   飞书要求事件回调 3 秒内返回且**不抛异常**，否则重推，用户收到重复消息。
4. **MATCH 必须写全三列同序**，否则报 1191。
5. **全文检索用 BOOLEAN，不用 NATURAL**。
