# Jotlog AI 润色规范

> 状态：v0.1定稿
> 前提：技术栈已改为 Java + Spring Boot + MySQL 8.0
> 关联：`Jotlog-技术选型.md`、`V1__init.sql`

---

## 一、先纠正一个用词

需求里说的"AI 润色"，在本项目里应该叫 **AI 补充**。

这不是文字游戏，它决定了表结构和数据能否长期可信。

| | 润色（错） | 补充（对） |
|---|---|---|
| 行为 | AI 改写用户原话 | AI 写入新字段 |
| 结果 | 原文被覆盖，无法追溯 | 原文永久保留 |
| 三个月后回看 | 一堆被洗过的漂亮废话 | 自己的想法 + 后来补的说明 |
| 失败代价 | 原文丢了，永久损失 | 只是摘要为空，可重跑 |

**数据库层面的硬约束**：`raw_input` 列永不被任何 UPDATE 语句触碰。
仓库层`EntryRepository` 刻意没有提供更新正文的方法，这是第一道防线；
`JdbcEntryRepository.applyAiResult()` 的 SQL 里不出现 `raw_input`，这是第二道防线。

## 二、四类内容，四种策略

用户随手记的东西不是一个种类。**用同一套 AI 逻辑处理它们是错的。**

| entry_type | AI 该做 | AI 不该做 | 原因 |
|---|---|---|---|
| `repo` 仓库 | 抓 README，说明"是干什么的 + 解决什么问题" | 不改写用户原话 | 仓库信息在README 里，不在用户的话里 |
| `link` 网址 | 抓正文，生成一句话摘要 | 不编造未抓到的内容 | 幻觉会让摘要完全不可信 |
| `video` 视频 | 只取标题和简介 | **不要总结视频内容** | B站/抖音/小红书大多抓不到正文，强行总结等于编造 |
| `note` 随记 | **完全跳过** | 绝不"优化"用户的原话 | 见下节 |
| `file` / `image` | 只做类型标注 | 不做内容理解 | M2 之后再谈 |

### 为什么 NOTE 类必须跳过

用户记下这句话：

> 人生不是要赶到哪里去，而是要学会欣赏沿途的风景

这句话不需要任何加工。它加任何"润色"都是噪音，是污染。

如果把金句交给 LLM"优化表达"，最可能的结果是把
"人生不是要赶到哪里去，而是要学会欣赏沿途的风景"
改成
"人生的意义不在于抵达远方，而在于欣赏沿途的风景"

改动很小，但这已经**不是用户当时的想法了**。用户记的是他自己的措辞，
三个月后回看时，他要找回的是"我当时怎么想的"，不是"AI 认为我该怎么想"。

**所以 NOTE 类的 `ai_status` 直接标记为 `skipped`，不调用任何模型。**

## 三、执行时机与顺序

飞书长连接要求事件回调 3 秒内完成，否则重推。因此顺序是铁律：

```
T+0     收到飞书消息
T+10ms  幂等检查（source + source_msg_id）
T+20ms  落库，拿到 id          ← 此刻数据已经安全
T+30ms  回复回执"已记下"       ← 用户确认收到
T+40ms  丢进增强队列，立即返回 ← 回调结束，不占飞书的时间
────────── 以下全部异步 ──────────
T+1s    抓取正文（超时 8 秒即放弃）
T+2s    调大模型生成摘要/标题/标签
T+3s    回写 ai_* 字段
T+3s    主动推送卡片给用户
```

铁律：**入库 → 回执 → 异步增强。**

任何慢操作放进同步路径，都会撞上 3 秒超时并导致消息重推、用户收到重复条目。

## 四、AI 只能写这些字段

允许写入：

| 字段 | 内容 |
|---|---|
| `title` | 一句话标题，用户没给标题时补 |
| `ai_summary` | 一到两句说明 |
| `ai_tags` | 逗号分隔的标签 |
| `ai_model` | 用了哪个模型，便于回溯效果 |
| `ai_latency_ms` | 耗时，用于后续优化 |

禁止写入：`raw_input`、`source_msg_id`、`created_at`、`content_hash`。

---

## 五、失败处理

AI 会超时、会限流、会返回格式错误。这些都是**预期内**的。

处理原则：

1. 失败**只影响摘要**，不影响记录本身。原文已经入库了。
2. 失败原因写进 `ai_error`，状态置`failed`。
3. **不自动重试到死**。最多 2次，间隔递增。
4. 永远可以在网页端手动补跑，不需要重发飞书。

一句话：**AI 挂了，Jotlog 依然是一个可用的随手记。**
这才是正确的依赖方向——AI 是增强，不是命脉。

## 六、摘要质量红线

LLM 返回的内容必须过一道校验，不合格就不写：

- **禁止编造链接内容**。如果正文抓取失败，摘要里不能说"这是一篇关于 X 的文章"——模型并不知道。
- 提示词里明确要求：只能基于给定材料，材料不足就说"信息不足"。
- 摘要长度上限 200 字。随手记的摘要不需要长文。
- 标签控制在 3-5 个。标签是为了筛选，不是为了展示。

建议的提示词骨架：

```
你在整理用户的私人随手记。

规则：
1. 只依据我提供的材料，不要补充任何材料之外的信息。
2. 材料不足时，直接说明"信息不足"，不要猜测。
3. 用中文输出，语气平实，不要营销腔。
4. 摘要不超过 100 字，标签 3-5 个，逗号分隔。

材料：
- 用户原话：{raw_input}
- 链接：{url}
- 抓取到的内容：{content}

输出 JSON：{"title":"", "summary":"", "tags":""}
```

`raw_input` 在提示词里的作用是**提供语境**（用户为什么存它），
不是**被改写的对象**。

## 七、模型选型

已确认：国内大模型 API（百炼 / DeepSeek / 智谱等）。

理由：
- 免费额度足够个人使用量级
- 中文摘要质量好于国际模型
- 走国内网络，不需要额外考虑出口问题

工程上用 LangChain4j 统一封装，换模型只改配置不改代码。
Spring Boot 3.5 用 `langchain4j-open-ai-spring-boot-starter`，
国内厂商基本都兼容 OpenAI 协议，配置 baseUrl 即可。

**接入时的一个提醒**：无论哪家模型，`ai_summary` 的可信度都取决于抓取是否成功。
模型再好也救不了没抓到的正文。所以抓取环节的失败率要单独监控。
